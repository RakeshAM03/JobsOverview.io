E2E execution flow

What happens when JOB-E2E-01 runs

Traced through the code for verifyCreateJobAndVerifyInOverview, from mvn clean test -Dsuitefile=e2e.xml to the closed job.

  1. Maven compiles and Surefire picks the suite. xmlfiles/${suitefile} resolves to e2e.xml, which includes only the e2e group across all 7 Jobs classes.
  2. TestNG registers three listeners. ChainTestListener, ReportListener, and RetryListener, which attaches RetryAnalyzer to every @Test.
  3. The data provider reads Excel. jobCreateData takes JOB-E2E-01 from the description, then ExcelReader returns that row from the job_create sheet. AUTO_QA_JOB_{UNIQUE} becomes something like AUTO_QA_JOB_20260929144644_415823.
  4. @BeforeMethod setUp runs. refreshGeneratedJobTitles issues a new unique title for this invocation (a retry gets its own title). BrowserFactory.startBrowser builds Chrome at 1920x1080 with implicit wait 0 and stores the driver in a ThreadLocal.
  5. Login. The browser opens https://platform.joveo.ai/<accountid>/jobs/jobs-overview and gets redirected to accounts.joveo.com. It enters the credentials from the login sheet (or -Dusername/-Dpassword), then waits for the platform URL and the Jobs Overview nav link. Login gets up to 3 attempts, with a browser restart between them.
  6. Navigate. DashboardPage.clickJobsOverview() returns JobsOverviewPage after waitForJobsOverviewToLoad(): URL, readyState, header button, and a settled grid.
  7. Open the drawer and fill it. clickJobRequisition() waits for the title “Create a job requisition”. fillMandatoryFields then fills title, station code ST01, Full-Time, California → Newport Beach, 92663, the URL apply path, the TinyMCE description, Hourly 20–40, and consent.
  8. Register cleanup before saving. registerJobForCleanup(title) runs before Continue is clicked. If the save succeeds and a later step fails, the job is still closed.
  9. Submit. clickContinue() captures the toast, retries with a JS click once if the drawer is still open with no message, waits up to 60 s for the drawer to close, then waitForJobToAppearInList.
  10. Verify. The test searches the unique title and expects count 1 in All Jobs and 1 in Active Jobs. On the job's Details tab, Employment Type Full Time, salary, unit, city, postal code and apply path must match the Excel row. All checks are soft asserts.
  11. Report. ReportListener logs pass or fail. On failure it saves screenshots/<method>_<timestamp>_<thread>.png and embeds it in ChainTest. This happens before teardown, while the browser is still alive.
  12. @AfterMethod tearDown runs. closeRegisteredJobs() opens Jobs Overview, searches the title in All Jobs (then Inactive Jobs), opens the job and sets status Closed. A cleanup error is logged, not thrown. The finally block clears the ThreadLocal list and quits the browser.
  13. Suite end. ChainTest writes reports/chaintest/Index.html and Email.html. ReportListener.onFinish prints any test that passed only after a retry as FLAKY.

Why the screenshot works on a failure: TestNG calls the listener's onTestFailure before @AfterMethod, so the driver still exists. Teardown is alwaysRun = true, so cleanup and quit() also run after a failed assertion.

60-second explanation

“Tell me about your framework”

I built a Java 21 hybrid Selenium framework for the Jobs module of Joveo's Talent Engage CRM. It uses Page Object Model and TestNG, with test data in Excel. There are six page objects: login, dashboard, Jobs Overview, and three components on top of it (filters, the Manage columns panel and the Create Job Requisition drawer), plus Job Details. The suite has 75 tests: 12 smoke, 60 regression and 3 end-to-end, each tagged with an ID like JOB-RG-24. The data provider uses that ID to pick its rows from the Excel sheet. The hardest part was the AG Grid. It virtualises rows and columns, so I read it through JavaScript that scrolls the grid horizontally and collects cells by col-id and row-index. I also wait for the grid text to stay unchanged for three polls, so I never assert on half-loaded data. Waits are explicit only, with no sleeps. Each test gets its own ThreadLocal browser, so the suite runs in parallel. Jobs created by a test get unique titles and are closed in teardown, which keeps the shared sandbox clean. ChainTest reports embed failure screenshots, and a single retry flags flaky tests instead of hiding them. The last regression run was 66 runs, 0 failures and 1 skip in about 16 minutes.

Design & structure Q1–Q7

Q1Why is the Jobs module split into six page classes instead of one big JobsPage?

Each class matches one UI region with its own lifecycle:

  • JobsOverviewPage is the grid page itself.
  • JobFiltersSection and JobColumnsPanel are components on that page. They are returned by getFiltersSection() and openManageColumns(), and their locators are scoped to a MuiPopover-paper.
  • JobCreateDrawer is an overlay scoped to MuiDrawer-paper.
  • JobDetailsPage is a separate route (/jobs-overview/<uuid>).

Navigation methods return the next page object: clickJobsOverview(), openJob(), clickBackArrow(), clickContinue() and confirmDiscardChanges(). Same-page actions return void. A test reads like the user journey, and a locator change touches one file.

Q2How does a test get from login to the Jobs Overview grid?
  • BaseClass.loginToApplication() opens ConfigReader.getJobsOverviewUrl(), which is qaenv + /<accountid> + /jobs/jobs-overview.
  • The app redirects to accounts.joveo.com. LoginPage.openApplication waits up to 45 s for input#email.
  • clickLogIn() waits for the platform URL, then gives DashboardPage.waitForNavigationMenu() up to 60 s for the Jobs Overview link.
  • Each test calls dashboardPage.clickJobsOverview(), which waits on URL, document.readyState, the header button and grid settle.

BaseClass.java · LoginPage.java · DashboardPage.java · ConfigReader.getJobsOverviewUrl()

Q3How does a test know which Excel rows belong to it?

Every description starts with the test case ID, e.g. "JOB-RG-67 - Verify Application URL validation". DataProviders.resolveTestCaseId takes the text before " - ", and ExcelReader.getDataForTestCase returns every row whose testcaseid matches.

Several rows mean several invocations. JOB-RG-67 runs three times (abc, www.x, a valid URL), so the 60 regression methods produce 66 runs. A missing ID fails fast with "No rows for JOB-RG-xx in sheet job_filter".

Q4What are your test groups and how do the suite XMLs use them?

TestGroups has smoke, regression, e2e, unauthenticated and createsdata. All four XMLs list the same 7 classes and filter by <include name="..."/>.

testng.xml uses parallel="tests" to run three blocks at once: Smoke (2 threads), Regression (3) and E2E (1, because those tests write data). A method with two groups runs once in each matching block.

-Dgroups=smoke activates the Maven profile run-by-groups, which runs testcases/**/*Test.java by group without an XML file and with -Dthreads threads.

Q5How does JOB-SM-12 test the redirect without logging in?

It is tagged {SMOKE, UNAUTHENTICATED}. BaseClass.requiresLogin(method) reads the @Test groups through reflection and skips login. The test calls LoginPage.openProtectedPage(jobsOverviewUrl) and asserts isLoginPageDisplayed(): the URL contains loginurlfragment (accounts.joveo.com), and the email, password and “Log in to Your Account” heading are visible.

Q6Why are there gaps in the IDs (no JOB-RG-02, RG-29 or RG-64 test)?

The IDs follow the Jobs test plan's numbering, and not every planned case is automated yet. Some Excel rows exist with no @Test yet: job_search has JOB-RG-29 rows for %, _, ' and <script>, job_validation has JOB-RG-64 ZIP code rows, and job_create has RG-04/76/77/81 and E2E-04/05. Keeping the plan's numbers makes traceability one-to-one, and those rows are the next candidates to automate.

Q7Where do assertions live, and why soft asserts in some tests?

Assertions live only in test classes; page objects return values (getJobCountFromHeader(), isContinueEnabled()). SoftAssert is used when one screen has several independent facts. JOB-SM-09 checks the drawer opened, the 4 section names, and that Continue is disabled. JOB-RG-87 checks 10 Details labels. One run then reports every broken label, not only the first. Hard asserts are used when a later step depends on the earlier one.

Tests also read state into variables before closing a popover, then assert afterwards. JOB-RG-44 reads checked, disabled and locked, calls closePanel(), then asserts, so a failure never leaves the panel open.

Waits & synchronisation Q8–Q13

Q8How do you know the Jobs grid has finished loading?

JobsOverviewPage.waitForGridToSettle() works in two steps:

  • waitForLoadersToDisappear() waits until no MuiCircularProgress, MuiLinearProgress, MuiSkeleton or ag-overlay-loading-wrapper is visible.
  • waitForTextToStabilize(gridState) concatenates the header title and count, every title cell and the pagination label. It waits until that text is identical for gridsettlepolls=3 consecutive polls, 500 ms apart.

A spinner disappearing does not mean the count is final. The header can show the old count for a moment, and a stable-text check catches that.

Q9After a search, how do you avoid asserting on the previous results?

searchJob() takes a snapshot of the grid text before typing, then calls waitForGridToChangeAndSettle(snapshot). That waits up to 6 s for the text to differ, then waits for it to settle.

The 6 s change wait is "quiet" (waitUntilQuietly returns false, no exception). Some actions legitimately don't change the grid; JOB-RG-28 searches " Job 1 " after "Job 1" and expects identical rows. The same pattern is used for selectView, sort, page size and every pagination button.

Q10Why is implicit wait 0?

With an implicit wait, every findElements blocks for the full timeout when nothing matches. Checks like isDisplayedNow, firstDisplayed and isAbsentWithin become slow and unpredictable, and mixing implicit with explicit waits can stack the timeouts. config.properties sets implicitwait=0 and explicitwait=20, and BasePage waits for the exact condition each action needs: visible to read, clickable to click, invisible for loaders, URL for navigation, frame for TinyMCE.

Q11How does BasePage.click handle MUI overlays and re-renders?
  • It waits for loaders, waits until the element is clickable, and scrolls it to the centre.
  • On ElementClickInterceptedException (a backdrop or loader on top), it waits for loaders again and retries a native click. If that is still intercepted, it falls back to a JS click.
  • On StaleElementReferenceException (React re-rendered the node), it finds the element again and clicks.

Every fallback is written to ChainTest through Utility.logStep, so the report shows when a JS click was needed.

Q12Where do you use FluentWait, and what does it ignore?

waitUntil(condition, description) and waitUntilQuietly(condition, maxWait) both build a FluentWait that ignores NoSuchElementException and StaleElementReferenceException. The first throws with a readable message (e.g. "Job not listed: AUTO_QA_JOB_..."); the second returns false. FluentWait is used for:

  • waitForJobToAppearInList after create
  • the State/City options narrowing to the search text
  • openTab waiting for aria-selected="true"
  • the Job Description accordion toggling aria-expanded
Q13A loader never disappears. Does the test hang or fail?

Neither. waitForLoadersToDisappear() uses a quiet wait, logs "A loader is still visible after 20s, continuing with element-level waits" and moves on. The next element wait decides the outcome. A decorative skeleton left in a corner then can't fail a test whose real content has loaded. waitForTextToStabilize behaves the same way.

AG Grid on Jobs Overview Q14–Q20

Q14Why do you read the Jobs grid with JavaScript instead of findElements?

AG Grid virtualises in both directions. Only the columns in the horizontal viewport exist in the DOM, and the DOM order of rows is not their visual order. COLUMN_VALUES_SCRIPT queries div[role=gridcell][col-id="…"], keys each cell by its row's row-index attribute, sorts by index and returns the values. getColumnValues() first calls scrollGridToColumn(columnId) so the column is rendered.

document.querySelectorAll('div[role=gridcell][col-id="' + colId + '"]').forEach(c => {
  const row = c.closest('[role=row]');
  rows[parseInt(row.getAttribute('row-index'), 10)] = c.innerText.trim();
});
Q15How do you collect all 23 column headers when only about 8 are rendered?

COLLECT_COLUMNS_SCRIPT runs through executeAsyncScript. It sets scrollLeft on .ag-body-horizontal-scroll-viewport and .ag-center-cols-viewport, moving max(200, clientWidth/2) pixels per step. After each step it waits two requestAnimationFrames so AG Grid can render, and collects col-id::label pairs. At the end it scrolls back to 0 and calls done(found). getAllColumnIds() and getAllColumnHeaderTexts() split those pairs. JOB-SM-03, RG-45, RG-46, RG-47 and RG-52 rely on it.

Q16Why address columns by col-id rather than header text?

col-id is the data field and doesn't change with labels or localisation: title, company, department, category, employmentType, status, createdAt, normalisedFields.city, normalisedFields.state, normalisedFields.country. Labels are used only where the label is what's being tested, as in JOB-SM-03's default columns “Job Title, Company, Department, Employment type, Job Category, Country, Country Code, District”.

Q17How do you prove “Created On” sorts by date and not as text?

JOB-RG-38 clicks the createdAt header, reads the column, and parses each value with DateTimeFormatter.ofPattern("dd MMM yyyy", Locale.ENGLISH) into a LocalDate. It then compares that list with a sorted copy. A text sort would put “02 Jan 2026” after “01 Aug 2026” and fail. The sort direction comes from the sort icon's SVG: the icon has no text, so getSortDirection reads the path's d attribute, and m4 12… means ascending.

Q18How do you verify a pinned column stays visible while scrolling?

JOB-RG-50 opens Manage columns, clicks Pin column to left on Status, and checks that button's aria-pressed="true". It closes the panel and scrolls the grid all the way to createdAt. It then asserts that the status header sits inside .ag-pinned-left-header. SCROLL_TO_COLUMN_SCRIPT skips scrolling for headers already in the pinned container.

Q19How do you compare the header count with pagination?

The header is a button with two h6 elements, the view name and the count. getJobCountFromHeader() runs Utility.extractFirstNumber on the second one. Pagination reads “1 to 25 of 87”, and getPaginationTotal() uses extractLastNumber, which also strips commas. JOB-SM-02 asserts the two are equal, and SM-04 repeats the check for All, Active and Inactive views.

Q20Some pagination tests skip. Why not just pass?

They depend on how many jobs the shared sandbox has right now:

  • JOB-RG-54 needs more than 25 jobs, because the smallest page size is 25.
  • JOB-RG-56 needs 25 or fewer.
  • JOB-RG-03 needs 0 inactive jobs.

They throw SkipException("Precondition not met: …") with the real total. A pass would claim coverage that didn't happen, and a fail would blame the product for test data. One of the RG-54/RG-56 pair always skips, which is the 1 skip in the last run.

Filters Q21–Q27

Q21Walk me through applyFilter("City", "Not In", ["New York City"]).
  • openFilter clicks the chip located by @aria-label starting with "City filter". The visible chip text changes to “City in New York City”, but the aria-label prefix stays the same.
  • For “Not In” it clicks the label of input[type=radio][value=NOT_IN].
  • selectValue opens the autocomplete if needed and clicks li[role=option] whose p equals the value.
  • clickApply waits for the popover to close and the grid to settle.
Q22How do you verify “Not In” really excludes values?

JOB-RG-11 reads the City column before filtering and counts the New York City rows. It applies Not In, then asserts that no remaining row is New York City and that the header count equals total − jobsInCity. The expected number comes from the app's own data, so the test doesn't break when someone adds a job.

Q23How do you test OR inside one filter and AND across filters?
  • OR (JOB-RG-12): Excel value New York City;Newport Beach is split on ;. Expected count = rows whose city is in either value; every result must be in the selected set; the chip must show both values or +1.
  • AND (JOB-RG-16): City In New York City + Employment Type In Full Time. The test reads both columns and checks them row by row by index. Both lists come from the row-index-sorted script, so index n is the same job in both.
  • Filter + search (JOB-RG-17): the same row-aligned check on title and city.
Q24Not every filter popover looks the same. How does one test method cover five filters?

JOB-RG-06…10 (City, Department, Employment Type, State Code, Postal Code) all call verifyFilterPopoverStructure(filterName). If the In radio appears within 3 s, it asserts that Not In is shown, In is the default, and the value search is present. Otherwise it logs that this filter is a checkbox list without operators and asserts that checkbox options exist. Both branches check that CLEAR is visible and APPLY is disabled until a value is chosen.

Q25What's the difference between CLEAR and Clear All in your tests?
  • CLEAR (JOB-RG-15): apply City + Employment Type, open City, click CLEAR. The City chip text resets to plain “City”, the Employment Type chip still shows its value, and the count goes up or stays the same.
  • Clear All (JOB-SM-07): the City chip resets, the count is at least the filtered count and equals the pagination total, and the Clear All link disappears (isAbsentWithin 5 s).
Q26How do you test the Add Filters menu?
  • JOB-RG-19 expects exactly City, Country, Department, Employment Type, Postal Code, State Code. Each option's tick (Mui-selected class) must match whether its chip is already in the bar. Chip names come from the aria-label text before " filter".
  • JOB-RG-20 adds Country, checks APPLY is disabled, ticks the first country checkbox, checks APPLY is enabled, applies, and verifies the chip text.
  • JOB-RG-21 clicks Postal Code (already active) and asserts the chip is removed.
Q27How do you check filter values come from real job data?

JOB-RG-22 builds a Set of the City column (minus N/A), opens the City filter's dropdown and reads the options. It asserts there are no duplicate options, every option exists in the data, and the two sets are equal. That catches stale or hard-coded option lists.

Create Job Requisition drawer Q28–Q38

Q28Which fields are mandatory, and how do you read them from the UI?

JOB-RG-58 expects Job title, Station code, Country, State, City, Application URL and Job description. getMandatoryFieldLabels() finds drawer elements containing a span with *, strips the asterisk, collapses whitespace, removes duplicates, and drops the consent text that starts with “By providing”.

Q29How do you prove Continue enables only when the form is valid?

JOB-RG-59 uses the BASE_FORM row and checks isContinueEnabled() after each field: title, station code, state, city, URL and description. It must stay disabled every time, including after the description while consent is pending. After acceptConsent() it must be enabled. BasePage.isEnabled checks three things, because MUI buttons can look disabled in three ways: the disabled attribute, aria-disabled="true", and a Mui-disabled class.

Q30State and City are searchable MUI selects. How do you pick “Newport Beach”?
  • openCityDropdown() clicks the div[role=combobox] after the “* City” label and waits for the listbox search input.
  • searchInOpenDropdown types the city, then waits up to 10 s until every option contains the text, then waits for stable text.
  • selectListboxOptionStartingWith("Newport Beach,") matches options in the “City, code” format with the trailing comma, so “Newport” can't match “Newport Beach”.
  • waitForTextPresent confirms the combobox shows the value.
Q31How do you type into the Job description editor?

It's TinyMCE inside iframe[id*='tiny-react']. enterJobDescription scrolls the iframe into view and calls switchToFrame (frameToBeAvailableAndSwitchToIt). It clicks body#tinymce, sends the text, then calls switchToDefaultContent(). Forgetting to switch back would make every later drawer locator fail with NoSuchElement.

The job_validation sheet holds only the field under test: value, secondvalue, expectedmessage, expectedvalue, expectedvalid. jobValidationData merges each row over a copy of job_create/BASE_FORM, so tests that need a complete form (RG-69, RG-71) get one. Real rows:

Q33How do you find the error message for a specific input?

helperTextFor(By input) turns the input's By back into its XPath (it strips the "By.xpath: " prefix). It then appends /ancestor::div[contains(@class,'MuiFormControl-root')][1]//p[contains(@class,'MuiFormHelperText-root')]. One method serves URL, email, min and max compensation and postal code, and errors from other fields can't match.

Q34How do you test the employment-type toggle exhaustively?

JOB-RG-61 first asserts Full-Time is the default. It then selects Part-Time, Contract, Temporary and Full-Time in turn, and after each choice checks all four buttons' aria-pressed, so exactly one is selected. That gives 16 state checks in one soft-assert block, which catches a toggle that allows two selections.

Q35How do you test the apply method switch and the tag inputs?
  • JOB-RG-66 clicks the URL, Email and WhatsApp cards. The required field label must change to Application URL, Email address and WhatsApp number.
  • JOB-RG-65 types Java + Enter and Selenium + Enter into Required qualifications, then adds Java again. The chips must stay [Java, Selenium] (no duplicate). Clicking Java's MuiChip-deleteIcon leaves [Selenium].
Q36How do you prove Cancel and X discard the form without creating a job?

JOB-RG-74 enters a unique title and station code and clicks Cancel. The “Discard changes?” dialog must appear, and the test confirms with Close. It reopens the drawer, types the title, clicks the X icon (lucide-x SVG), checks for the dialog and confirms again. It then searches that unique title on Jobs Overview and asserts No data. Because the title is unique, an empty result proves nothing was saved.

Q37Continue sometimes did nothing on the first click. How did you handle it?

clickContinue() clicks and then waits up to 15 s to capture any toast into submissionMessage. If the drawer is still open, there's no message, and Continue is still enabled, it logs the case and fires one JS click. It then waits up to 60 s for the drawer to close and settles the grid. It never clicks twice when a toast appeared, so it can't create duplicate jobs.

Q38Validation tests open the drawer but never save. How do they leave it?

closeDrawerDiscardingChanges() clicks Cancel and confirms the discard dialog only if it appears within 5 s. Then it waits for the drawer to close. RG-59, RG-69 and RG-71 call it before their hard asserts, so the drawer state is captured and closed even when the assertion fails.

Job Details Q39–Q44

Q39How do you verify the header on the Job Details page?

JOB-RG-78 searches the baseline job “July 24 - QA test update” and reads city, state and country from that grid row first. It then opens the job and asserts:

  • the title matches
  • the Job ID matches [0-9a-f-]{36} (a UUID)
  • the location equals city + ", " + state + ", " + country
  • the status button is not blank

The grid is the expected value, so the test checks consistency between two screens, not a hard-coded string.

Q40How is the job status changed, and where is it used?

JOB-RG-80 opens the status popover and asserts the heading “Status”, the options [On Hold, Closed], and Apply disabled until a choice is made. changeStatus("Closed") opens the popover, selects the option, clicks Apply, captures the toast and waits for the page. Its main user is BaseClass.closeRegisteredJobs() during teardown.

Q41What do you check on the Applicants tab?
  • JOB-RG-83: the filters start with Applicant Stages, Talent Match, Applied On and Active Applicant. It uses startsWith because chip text includes counts.
  • JOB-RG-84: search a candidate name from Excel; every candidateFullName cell contains it, ignoring case, and the list isn't empty.
  • JOB-RG-85: Bulk Actions and “Move Application to” are disabled, then enabled after ticking the first row's checkbox (aria-label starts with “Press Space to toggle row selection”).
Q42How do you read label/value pairs on the Details tab?

One dynamic locator, //p[normalize-space()='<label>']/following-sibling::*[1], covers every pair. JOB-RG-87 loops over Employment Type, Min salary, Max salary, Salary Unit, Salary Currency, Company Name:, City:, Province:, Postal Code: and Apply Path:. Each must be visible and non-blank. The trailing colons are part of the UI labels.

Q43How do you test the Job Description accordion?

JOB-RG-90 reads aria-expanded on the MuiAccordionSummary button: false by default, true after one click, false after the second. clickJobDescriptionHeader() stores the state before clicking and uses waitUntil for it to flip. That avoids reading the attribute during the animation.

Q44How does search by full Job ID work end to end?

JOB-RG-24 opens the baseline job, reads the UUID from the header, clicks the back arrow (which waits for Jobs Overview to load), and searches that UUID. The grid must contain exactly [July 24 - QA test update]. The ID is never stored in Excel, because it would differ between environments.

Test data & parallel safety Q45–Q50

Q45Which jobs do tests use: existing ones or ones they create?

Both, on purpose.

  • Read-only tests (search, details, applicants) use a stable baseline job, “July 24 - QA test update”, from the job_details and job_search sheets. They never change it.
  • Tests that create data (JOB-E2E-01…03, tagged createsdata) make their own AUTO_QA_JOB_{UNIQUE} job and close it afterwards.
Q46How is {UNIQUE} generated, and why regenerate it in @BeforeMethod?

Utility.generateUniqueValue returns prefix + yyyyMMddHHmmss + "_" + threadId + random(1000–9999). ExcelReader resolves {UNIQUE} once, when the data provider runs. A retry reuses the same Map, so the retried test would try to create a job whose title already exists from the first attempt. BaseClass.refreshGeneratedJobTitles(parameters) replaces any jobtitle starting with AUTO_QA_JOB_ before every invocation, including retries.

Q47How do you guarantee created jobs get cleaned up?
  • registerJobForCleanup(title) runs before Continue is clicked, into a ThreadLocal<List<String>>.
  • @AfterMethod(alwaysRun = true) runs closeRegisteredJobs(): open Jobs Overview, All Jobs, search; if not found, try Inactive Jobs; if still missing, log “already closed or not found”; otherwise open it and changeStatus("Closed").
  • Each job is in its own try/catch, so one failed cleanup doesn't skip the rest. A finally block removes the ThreadLocal and quits the browser.
Q48What makes the suite safe to run in parallel?
  • A ThreadLocal<WebDriver> in BrowserFactory, and a new browser plus login per test method.
  • A ThreadLocal cleanup list, so threads never close each other's jobs.
  • Unique titles that include the thread ID.
  • Data providers declared parallel = false and data-provider-thread-count="1", so rows of one method don't race each other.
  • Count assertions after data changes are scoped to the test's own title. JOB-E2E-01 searches its title and expects 1, never “total + 1”, because other threads change the total.
Q49Why does a fresh browser per test matter for Jobs specifically?

Jobs Overview keeps UI state. JOB-RG-52 shows that a hidden column stays hidden after a refresh, and JOB-RG-23 checks filter state after back and refresh. A fresh browser profile per test means a column hidden by RG-45, or a filter left by RG-11, can't change what SM-03 or SM-06 see in the next test.

Q50Why DataFormatter in ExcelReader?

Because the Jobs data is full of numbers that must stay text: postal code 92663, a 10-digit WhatsApp number, station code, compensation 20/40, and repeat counts like 129/500. Reading them as numeric cells would give 92663.0 or 9.16435065E9. DataFormatter.formatCellValue returns exactly what the cell shows.

Reporting, retry & config Q51–Q55

Q51How do retries work, and how do you keep them honest?

RetryListener is an IAnnotationTransformer that sets RetryAnalyzer on every @Test, with retry=1 from config. When a test passes after a retry, ReportListener.onTestSuccess logs FLAKY: … passed after 1 retry to ChainTest. onFinish prints the suite's flaky list, or “No flaky tests detected”. A retry is treated as a signal to investigate, not a fix.

Q52What goes into the report for a failed Jobs test?
  • Every Utility.logStep line: each click, each typed value (shortened to 60 chars; the password shows as ********), and every fallback.
  • The full failure message, plus the first line on the console as [FAILED] method [JOB-RG-xx - …] -> reason.
  • A screenshot embedded as image/png, saved as screenshots/verifyDuplicateJobTitleHandling_20260929_153911_889_34.png (method, timestamp, thread).
Q53Why a fixed 1920x1080 window, even headless?

The window width decides how many AG Grid columns are rendered, where the horizontal scrollbar ends, and whether the drawer's sections fit on screen. Chrome gets --window-size=1920,1080 and the size is set again after startup. Headed, headless and CI runs then see the same grid, and the scroll steps in the column scripts behave the same.

Q54What is driverreadtimeout=90 for?

It's the HTTP read timeout between Selenium and the driver, set through ClientConfig.defaultConfig().readTimeout(...). Without it, a hung Chrome session could block one thread of the parallel run for a long time. With it, the command fails after 90 s, the test fails or retries, and the run continues. It is separate from pageloadtime=60 and scripttimeout=30, which bound the async grid scripts.

Q55How do you switch environment, browser or credentials?

ConfigReader.getValue checks System.getProperty first, then config.properties. -Denv=stage switches to stagenv, -Dbrowser=edge -Dheadless=true changes the browser, and -Dusername=… -Dpassword=… override the login sheet. Headless is also forced when the CI environment variable is true.

Scenarios · problems met on the Jobs module

Scenario questions

Answer each as: what you saw, how you confirmed the cause, the fix in code, and what stops it coming back.

S1The search test passed locally but failed in parallel with “Title should contain search text”.

Cause: the assertion read the rows that were on screen before the search request returned. Fix: searchJob snapshots the grid text before typing and waits for it to change and then settle (waitForGridToChangeAndSettle). Prevention: every action that changes the grid (view, sort, page size, pagination, column menu) uses the same pattern.

S2“Column should disappear from the grid” failed even though Company was hidden on screen.

Cause: a findElements check for headers only sees rendered columns, and the result depends on scroll position. Fix: getAllColumnIds() scrolls the whole grid with the async script and collects col-ids, so “contains company” is a statement about the grid, not the viewport.

S3After selecting a City in the drawer, Continue could not be clicked: the dropdown was still open.

Cause: the MUI listbox sometimes stays rendered after selection, with a backdrop on top. Fix: closeOpenDropdown() tries a ladder of steps, each only if the previous one didn't work: Escape in the search box, Escape twice, a JS click on the last MuiBackdrop-root, a click on the drawer title, and finally a log line. BasePage.click handles any remaining interception with retry and a JS fallback.

S4A failed E2E run left AUTO_QA_JOB_ requisitions active in the sandbox.

Cause: registration happened after verification, so a failed verification skipped cleanup. Fix: registerJobForCleanup now runs before Continue, and tearDown is alwaysRun with cleanup in try/finally. Cleanup also checks Inactive Jobs, so a job closed by the test isn't treated as an error.

S5A retried E2E test failed with a duplicate job title.

Cause: {UNIQUE} resolves when the data provider reads Excel, and a retry reuses that row, so it reused the title from attempt one. Fix: refreshGeneratedJobTitles in @BeforeMethod gives every invocation a new AUTO_QA_JOB_ title, and the thread ID in the value keeps parallel threads apart too.

S6The pagination test went red after someone archived jobs in the sandbox.

Cause: “next page” assertions assumed more than 25 jobs. Fix: RG-54 and RG-56 read getPaginationTotal() and throw SkipException with the real number when their precondition doesn't hold. The report shows that the data was missing, not that the product was broken.

S7Sort on Created On “passed”, but the dates were in the wrong order.

Cause: comparing strings. “01 Aug 2026” sorts before “02 Jan 2026” as text. Fix: parse with dd MMM yyyy and Locale.ENGLISH (so a non-English machine doesn't break month names) into LocalDate, then compare with a sorted copy.

S8The Department filter test failed with NoSuchElement on the In radio.

Cause: not every filter has In/Not In. Some show a checkbox list. Fix: verifyFilterPopoverStructure checks isInOperatorDisplayed() with a 3 s quiet wait and branches, logging which type of popover it found. One helper now covers five filter tests.

S9Login randomly timed out on the SSO page during parallel runs.

Cause: slow redirects to accounts.joveo.com when several browsers start together. Fix: a 45 s quiet wait for the email field, a 60 s wait for the nav menu, and loginWithRetries(browser, 3), which quits and restarts the browser between attempts and logs each failure reason.

S10A test failed with “Header count should equal pagination total”: 0 vs 87.

Cause: the header rendered “(0)” for a moment while the grid loaded. The loader had gone, but the data hadn't arrived. Fix: the settle check includes the header h6 text and needs 3 identical polls, so a transient 0 never gets read.

FAQs · using the project

Practical questions

F1How do I run only the Jobs smoke tests, headless, on Edge?
mvn clean test -Dsuitefile=smoke.xml -Dheadless=true -Dbrowser=edge
mvn clean test -Dsuitefile=regression.xml
mvn clean test -Dsuitefile=e2e.xml
mvn clean test -Dgroups=smoke -Dthreads=2      # profile run-by-groups, no XML
mvn clean test                                  # testng.xml: smoke + regression + e2e in parallel
F2Where do I find the results?
  • ChainTest HTML: reports/chaintest/Index.html
  • ChainTest e-mail: reports/chaintest/Email.html
  • TestNG/Surefire: target/surefire-reports/index.html and TestSuite.txt
  • Screenshots: screenshots/<method>_<timestamp>_<thread>.png
F3How do I add a new Jobs test, e.g. JOB-RG-29 special characters in search?
  • The rows already exist in job_search (%, _, ', <script>alert(1)</script>).
  • Add a method to JobSearchTest with groups = {TestGroups.REGRESSION}, dataProvider = "jobSearchData", and a description starting "JOB-RG-29 - ".
  • Use existing page methods: searchJob, isNoDataDisplayed, isErrorToastDisplayed, and wasAlertTriggered for the script case.
  • New class? Add it under <classes> in all four XMLs.
F4How do I add a new page or component?

Create it in src/main/java/pages, extending BasePage. Use private final By fields and private methods for dynamic locators. Navigation methods return the next page object after its waitFor… method; same-page actions return void. Don't add assertions, comments or Thread.sleep.

F5A test needs a job that nobody else touches. What do I do?

Put AUTO_QA_JOB_{UNIQUE} in the jobtitle cell, create the job through fillMandatoryFields, and call registerJobForCleanup(title) before clickContinue(). Tag the test TestGroups.CREATES_DATA. After the create, scope every count to that title.

F6What are the known limitations I should be ready to discuss?
  • The column-read scripts see only the current page of rows (default 25). JOB-RG-11, RG-12 and RG-22 compare the header total with those rows, so they assume the matching jobs fit on one page. Next step: set page size to 100, or read totals from pagination.
  • JOB-RG-23 asserts the filter state after Back equals the state after Refresh, not that it persists, because the expected behaviour wasn't specified.
  • Read-only tests depend on the baseline job “July 24 - QA test update” existing in the sandbox.
  • The README lists Surefire 3.6.0, but pom.xml pins 3.5.2.
